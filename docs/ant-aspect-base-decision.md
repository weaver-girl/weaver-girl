# 切面底座决策

读到的公开材料把安全平行切面拆成三层，weaver-girl 只占最下面一层。

## 公开模型

电信终端产业协会 T/TAF 162—2023《移动应用安全平行切面技术指南》（2023-04-26 发布并实施）把移动端切面组件分成底座和管控。底座承担四件事：配置读取、切点植入、数据上报、模块加载。管控放具体的切点处理，按场景换成不同模块，再经底座把观测送出去。公开著录把蚂蚁科技集团股份有限公司列为起草单位之一。这次没有下到该 PDF 的字节（`taf.org.cn` 空回复 / TLS 失败），架构分工来自同一 URL 已被索引的正文，起草单位来自该标准的公开著录页，不是前言页的逐字核对。

中兴通讯技术 2022 年 12 月（第 28 卷第 6 期，DOI `10.12142/ZTETJ.202206011`）韦韬、顾为群、刘宇江《安全平行切面：面向企业数字生命体的安全基础设施》把同一想法放到运行时架构上。业务空间旁边有一块平行空间；不改源码、靠注入或代理加进去的逻辑叫切面应用。切面应用跑在切面平行舱里。平行舱要有隔离、可调度、可管控：各自的依赖不污染业务空间，切面核心按优先级调度，应用异常由核心挡住，核心自己异常则由统一代理兜底，业务调用照旧返回。大规模部署再分成切面安装器、切面核心、切面应用；云端管控端决定给哪种语言装哪一版。RASP、IAST 和数据血缘在这篇文章里是切面应用，不是底座。

《安全平行切面总体技术要求》在刘宇江 2025 年 11 月的公开访谈里被说成已通过团体标准评审、还在发布流程中。全文没有取到，所以不拿它当实现规格，也不补写它的条款。

JVM-Sandbox 的事件模型和 SOFAArk 的类隔离是别的先有技术，不是上面这两份材料定义的切面标准，本仓库不把它们当成这套标准来实现。

## 决定

weaver-girl 就是切面底座，不是切面应用，也不是切面管控。

底座四项里，这个仓库已经有的是：

- 配置读取：本机 YAML（见 `docs/yaml-config-reference.md`）。读的是随进程提供的文件，不是云端切面管控平台下发的配置。
- 切点植入：`WeaverTransformer` 用 Byte Buddy 按已注册的切点改类。一个类在变换里抛出（含 `Error`）时不安装新字节，原方法仍可调用，同一次安装里的其他类继续增强，进程不退出。失败记在 `AgentDiagnostics`，由现有的 `GET /diagnostics/faults` 列出。
- 数据上报：`JsonEventListener`、Prometheus 导出，以及 `AgentApiServer` 上的 `GET /events`、`GET /diagnostics/faults`、`GET /jvm`。对象是本进程的操作员，不是云端管控平台。
- 模块加载：拦截器注册表、插件模块，以及 `AnnotationPluginLoader`。

平行舱那三项（隔离、可调度、可管控）里，本仓库只落到「一个类变换失败不拖垮 JVM 和兄弟类」。没有按切面应用划分的命名空间，没有按优先级调度多个切面应用，也没有按许可收紧应用能做的动作。

明确不做上层：云端控制面、阻断或 NbSP 白名单、RASP 或可信模块，以及移动端、内核、服务网格上的切点。这些留在切面应用和切面管控，不进这个代理。

本决定不改变生产字节码，编译目标仍是 Java 8。
